# Automated Ontology Evaluation in LLM Generation Context

## What Method Outputs Can and Cannot Support as Quality Claims

This repository contains the research materials, evaluation scripts, input ontologies, and result tables for an MSc thesis on automated ontology evaluation in the context of LLM-generated ontologies.

The thesis investigates a central methodological problem: automated ontology evaluation methods produce numbers, flags, matches, and reports, but those outputs do not all support the same kind of quality claim. A metric may show that an ontology is syntactically parseable, structurally rich, lexically close to a source text, able to answer selected competency questions, or similar to a reference ontology. These are different claims. Treating them as interchangeable evidence of "ontology quality" risks over-interpreting narrow outputs.

This project therefore separates:

1. **Evaluation approach**: what the method actually does.
2. **Method output**: what evidence the implementation produces.
3. **Quality concern**: what aspect of ontology quality the output speaks to.
4. **Quality claim**: what can and cannot reasonably be concluded from that output.

## Research Context

The evaluated ontologies were generated for two domains:

- **Music**
- **Hospital / healthcare narrative**

For each domain, the repository includes:

- a generated ontology;
- a reference ontology;
- competency questions;
- a domain source story used for term profiling;
- generated result files from the selected evaluation approaches.

The repository is designed to be readable by someone who did not build the project. The active evaluation code is intentionally narrow: exploratory methods that were not part of the final comparison have been removed from the active runner and results structure.

## Evaluation Approaches

### Implemented In The Python Runner

The main script, `evaluation/evaluation_phase_II.py`, currently runs five evaluation approaches.

| Approach | Main output | What it can support | What it cannot support by itself |
|---|---|---|---|
| Basic statistics | Entity, axiom, annotation, and triple counts | Descriptive claims about ontology size and representational profile | Correctness, usefulness, or conceptual adequacy |
| OQuaRE | Raw metrics, scaled scores, subcharacteristics, characteristics | Claims about structural and model-quality indicators defined by the implemented OQuaRE mapping | Domain truth, modelling correctness, or user fitness without interpretation |
| Competency question coverage | SPARQL queries, answer rows, answerability flags | Claims about whether the ontology graph can answer the encoded CQs | Whether the CQs are complete, whether answers are semantically correct beyond the encoded data |
| Brewster-style vocabulary profile similarity | Token overlap, cosine similarity, weighted precision/recall/F1 | Claims about lexical overlap between ontology vocabulary and source text | Conceptual correctness or relation-level modelling quality |
| Maedche-Staab similarity | Lexical, taxonomic, and relation-overlap comparison tables | Claims about similarity to a reference ontology | Whether the reference is complete, correct, or the only valid modelling choice |

### External Result Folders

The repository also reserves result folders for two external tools:

| Tool | Folder | Role |
|---|---|---|
| OOPS! | `results/oops/` | Ontology pitfall scanning outputs |
| FOOPS! | `results/foops/` | FAIR ontology assessment outputs |

These folders are placeholders for manual/exported reports. They are not generated by `evaluation/evaluation_phase_II.py`.

## How To Reproduce The Active Results

Run from the repository root:

```powershell
python evaluation\evaluation_phase_II.py
```

This regenerates:

- `results/basic_statistics/basic_statistics_summary.csv`
- `results/oquare/*.csv`
- `results/cq_coverage/*.csv`
- `results/vocabulary_profile_similarity/*.csv`
- `results/maedche_staab_music/*.csv`
- `results/maedche_staab_hospital/*.csv`
- `results/evaluation_results.json`

The OOPS! and FOOPS! folders are not regenerated by this command.

## Notes On Interpretation

The project deliberately avoids treating one automated score as a direct proxy for overall ontology quality.

Important limitations:

- A high **basic statistics** count does not mean the ontology is correct.
- A high **OQuaRE** score depends on the implemented metric mapping and threshold choices.
- A positive **CQ coverage** result means the encoded query returned data, not that all possible competency requirements are satisfied.
- A high **vocabulary profile** score indicates lexical overlap, not necessarily correct conceptual modelling.
- A high **Maedche-Staab** similarity score indicates closeness to a chosen reference, not absolute quality.
- OOPS! and FOOPS! reports should be interpreted as external tool outputs with their own assumptions and coverage limits.

The thesis uses these outputs as evidence for bounded quality claims, not as unrestricted quality judgements.

## Card-Sort Materials

The `card-sort/` and `data/card-sort-outcome/` folders contain materials from the card-sort component of the research. They are kept separate from the ontology evaluation runner.

The root-level card-sort heatmap files in `results/` are study artifacts, not active ontology evaluation outputs.
